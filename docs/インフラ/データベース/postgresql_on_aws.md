# AWSでなるべく安いPostgreSQL環境

前提: 個人開発〜小規模だが将来本番運用もありうる想定。東京リージョン(ap-northeast-1)、2026年8月時点のおおよその料金(変動あるので目安)。

## 結論(決定): RDS for PostgreSQL 3年RI・前払いなしを採用

- **採用構成**: RDS for PostgreSQL, `db.t4g.micro`, Single-AZ, gp3 20GB, 非公開(VPC内からのみアクセス)
- **購入方式**: 3年リザーブドインスタンス・**前払いなし**
- **月額目安**: 約 $12〜13(ストレージ込み)。想定していた予算上限の$15以内に収まる
- **EC2自前構築(パブリックサブネット+NATなし)は不採用**。詳細な比較は以下に残すが、判断理由は次の通り。
  1. EC2自前の月額目安(約$10〜12)とRDS 3年RI前払いなしの月額目安(約$12〜13)がほぼ同水準まで縮まった
  2. コストが並ぶなら、単一障害点・自前パッチ/バックアップ・Lambdaからのコネクションプール管理といった運用リスクをRDSに肩代わりしてもらう方が割に合う
  3. 「前払いなし」を選ぶことで、全前払い(3年で一時金 約$220〜260)を払うリスクも取らずに済む
  4. 3年間インスタンスクラスが固定される点は、サービスを3年以上続ける前提(副業として育てる想定)であれば許容範囲

以降の節は、この結論に至るまでの比較検討の記録として残す。

## 選択肢比較(DB本体のみ、ネットワーク費用は別枠で後述)

| 方式 | 月額目安 | メリット | デメリット |
| --- | --- | --- | --- |
| **EC2自前インストール** (t4g.micro + EBS gp3 20GB) | 約 $7〜8 | 圧倒的に安い。構成の自由度が高い | OS/PostgreSQLのパッチ・バックアップ・監視を自分で運用する必要がある |
| **Lightsail マネージドDB** (Standard, 1GB RAM/40GB SSD) | $15固定 | 料金が固定でわかりやすい。バックアップ・パッチ適用が自動 | スペック変更の柔軟性が低い。EC2よりは割高 |
| **RDS for PostgreSQL** (db.t4g.micro + gp3 20GB, オンデマンド) | 約 $25〜30 | フルマネージド。自動バックアップ、Multi-AZ、リストアが容易 | オンデマンドでは選択肢の中で高め |
| **RDS for PostgreSQL 1年RI (前払いなし)** | 約 $18〜21 | オンデマンド比 約29〜34%引。前払い不要 | 1年間そのインスタンスクラスに縛られる |
| **RDS for PostgreSQL 1年RI (全前払い)** | 月換算 約 $15〜18 + 契約時に一時金 | 割引率が最も高い(前払いなし/一部前払いより有利) | 初期にまとまった支払いが必要、途中解約しても返金なし |
| **RDS for PostgreSQL 3年RI (全前払い)** | 月換算でさらに下がる(目安 $10〜13) | 運用が固まっているなら最安のRDS運用 | 3年間のコミットは小規模開発初期にはリスクが大きい |
| **Aurora Serverless v2** | 約 $40〜(最小0.5ACU) | 自動スケール、使わない時間帯は縮小 | 最小構成でも常時課金が発生し、小規模用途では逆に割高になりやすい |

- EC2は無料利用枠(750時間/月)が2025年7月以降の新規アカウントでは廃止済み。t4g.smallのみ2026年末まで無料トライアルが継続中。
- ストレージはどの方式でもEBS gp3ベースなら1GBあたり月$0.096〜0.115程度が目安。
- RIの割引率・実額は時期とAWSの価格改定で変動するため、契約前に必ず [AWS Pricing Calculator](https://calculator.aws) で ap-northeast-1 / db.t4g.micro / PostgreSQL / Single-AZ の最新値を確認すること。

## VPC・ネットワークコストの実態(「EC2は結局高くなる」の正体)

EC2自前構築が「圧倒的に安い」のはDB本体だけを見た場合であり、**ネットワーク構成次第でRDSより高くなる**ことがある。ここが「単純なEC2も検討したが、結局VPCやネットワークのコストで高くなる」という印象の正体。

### コストが跳ねる主因

1. **NAT Gateway**: プライベートサブネットに置いたEC2からOSパッチ(`dnf update`)やパッケージ取得のために外向き通信をさせると、NAT Gatewayが必要になる。NAT Gatewayは通信量ゼロでも**時間課金が固定費として発生**し、目安で月$45前後(リージョン・時期により変動、別途データ処理料金 $0.045〜0.062/GB程度が加算)。DB本体が月$7〜8なのに、NATだけでその5〜6倍のコストがかかり、RDSオンデマンド($25〜30)より高くなる。
2. **パブリックIPv4アドレス課金**: 2024年2月以降、EIPに限らずEC2の自動割当パブリックIP・NAT Gatewayの持つ公開IP・RDSの公開エンドポイントなど、稼働中のパブリックIPv4アドレス1つにつき $0.005/時間(月換算 約$3.6)が課金される。数は少ないが「無料だと思っていたもの」に課金される点に注意。
3. **RDSのパブリックアクセス**: RDSを`publicly accessible`にすると上記のパブリックIPv4課金対象になる。アプリと同一VPC内からのみアクセスする構成(非公開)にしておけば、この課金は発生しない。

### 対策: NAT Gatewayを使わない構成にする

EC2自前構築を最安に保つには、そもそもNAT Gatewayを使わない設計にするのが要点。

- EC2をパブリックサブネットに置き、セキュリティグループで自分の開発環境IP/アプリサーバーのSGのみに5432番等を絞る(0.0.0.0/0は厳禁)。これならNAT不要で、コストはパブリックIPv4課金の月$3.6程度で済む。
- 完全にパブリックIPを持たせたくない場合は、S3 Gateway型VPCエンドポイント(無料)経由でAmazon Linuxのリポジトリにアクセスできないか検討する(要検証。CloudFront経由のリポジトリだと効果がない場合がある)。
- **RDSはそもそもDB自体がNATを必要としない**(パッチ適用やバックアップはAWS側で完結する)。ネットワークコストで比較する場合、NAT Gatewayが必要になるのは基本的に「自分で管理するEC2を外部通信させる」場合であり、RDSを使う限りこのコストは発生しない。これがRDSの見えにくいメリット。

### 結論(ネットワークコスト込み)

| 構成 | 月額目安(DB+ネットワーク) |
| --- | --- |
| EC2自前(パブリックサブネット、NATなし) | 約 $10〜12 |
| EC2自前(プライベートサブネット + NAT Gateway) | 約 $55〜70以上 |
| RDS オンデマンド(非公開) | 約 $25〜30 |
| RDS 1年RI 前払いなし(非公開) | 約 $18〜21 |
| RDS 1年RI 全前払い(非公開) | 月換算 約 $15〜18 |

→ **NATを使わない設計にできるならEC2自前が依然として最安**。一方、プライベートサブネット構成が前提(セキュリティ要件などで公開サブネットを避けたい)なら、NAT Gatewayのコストが重く、**RDS(特に1年RI)の方が総額で安くなる**逆転が起こる。

## 検討時の整理(決定前のメモ、参考)

コスト最優先なら **EC2 (t4g.micro or t4g.small) にPostgreSQLを直接インストールし、NAT Gatewayを使わない設計にする** のが最安ではあった。
ただし本番運用も見据えると、以下の運用コストを許容できるかが課題になる。

- OSパッチ・PostgreSQLのマイナーバージョンアップは自分で実施
- バックアップはEBSスナップショットの定期取得を自分で設定(cron + AWS CLI、またはAWS Backup)
- 単一AZ構成になるため、AZ障害時は落ちる
- 見えないコスト(自分の作業時間)を考慮する

小規模でも「運用の手間をかけたくない」場合はLightsailマネージドDBが固定$15/月で妥協点になり得るが、今回は上記「結論」の通りRDS 3年RI・前払いなしを採用した。

RIの支払いパターン別の月額目安は以下の通り(インスタンス`db.t4g.micro`、ストレージ込み)。

| 支払い方法 | 割引率目安 | 月額目安 | 契約時の支払い |
| --- | --- | --- | --- |
| 3年RI・前払いなし(**採用**) | 約40〜45%引 | 約$12〜13 | $0 |
| 3年RI・一部前払い | 約48〜52%引 | 約$11〜12 | 中間額 |
| 3年RI・全前払い | 約58〜63%引 | 約$9〜10 | 一時金 約$220〜260 |

## 構築方針(採用: RDS)

1. RDS for PostgreSQL(`db.t4g.micro`, Single-AZ, gp3 20GB)をまずオンデマンドで起動する。`publicly accessible`は無効にし、Lambdaと同一VPC内からのみアクセスできるようにする。
2. Lambdaを同一VPCにアタッチし、RDSのプライベートエンドポイントへ接続する(詳細は [アーキテクチャ/API基盤.md](../../アーキテクチャ/API基盤.md) を参照)。
3. 動作確認ができたら、**同一インスタンスクラス/AZ/デプロイ形態(Single-AZ)で3年RI・前払いなしを購入する**。RI購入は稼働中のオンデマンドインスタンスに事後適用される課金上の仕組みなので、インスタンスを作り直す必要はない。
4. バックアップはRDSの自動バックアップ(デフォルト保持期間、必要に応じて延長)に任せる。追加で`pg_dump`によるロジカルバックアップをS3にエクスポートしておくとより安全。

## 参考: EC2自前構築の手順(不採用、検討時のメモ)

### 1. インスタンス起動

- インスタンスタイプ: `t4g.micro` (2vCPU/1GB, Graviton, ARM64) ※メモリが厳しければ `t4g.small` (2GB)
- AMI: Amazon Linux 2023 (ARM64)
- ストレージ: gp3, 20GB程度から(必要に応じて拡張)
- ネットワーク: **パブリックサブネットに配置しNAT Gatewayを使わない**(前述のネットワークコスト対策)。セキュリティグループで5432番ポートは自分の開発環境のIP、またはアプリケーションサーバーのセキュリティグループのみに限定(0.0.0.0/0は厳禁)

### 2. PostgreSQLインストール

```bash
sudo dnf update -y
sudo dnf install -y postgresql16 postgresql16-server
sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql
```

### 3. 初期設定

- `postgresql.conf` の `listen_addresses` をアプリケーションサーバーからの接続に合わせて設定(全開放しない)
- `pg_hba.conf` で接続元IP/セキュリティグループを絞る
- 管理用ユーザーのパスワードを設定し、アプリ用ユーザー/DBを個別に作成(rootユーザーを直接使わない)

### 4. コスト最適化のポイント

- **NAT Gatewayを作らない**(パブリックサブネット + SGでアクセス制限)。前述の通りNAT Gatewayの固定費が最大の落とし穴で、これを避けられるかどうかでEC2自前構築が最安になるかRDSより高くなるかが決まる
- パブリックIPv4アドレスは2024年2月以降1つにつき月$3.6程度課金される(EIPも自動割当パブリックIPも同様)。使わないEIPは解放する
- 開発用途で常時起動不要なら、夜間/週末はインスタンス停止でEC2稼働時間そのものを削減できる(EBS分の料金は停止中も発生)
- EC2自体のリザーブドインスタンス/Savings Plansは1年以上の運用が確定してから検討(小規模開発初期はオンデマンドで様子見でよい)

### 5. バックアップ運用

- 最低限、EBSスナップショットを日次で自動取得(AWS Backupのバックアッププランが簡単)
- `pg_dump` によるロジカルバックアップも併用し、S3に定期エクスポートしておくとより安全

## 将来的な移行の目安

- サービスが成長してダウンタイムが許容できなくなったら、Single-AZからMulti-AZへの変更を検討(RDSはコンソール操作でMulti-AZ化が可能、再構築は不要)
- 同時アクセスが増えてコネクション数が問題になったら、RDS Proxyの追加を検討(追加コストはかかるがLambdaからのコネクションプーリングを引き受けてくれる)
