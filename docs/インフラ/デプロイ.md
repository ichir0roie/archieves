# 本番へのデプロイ

画面は Amplify Hosting、API は Lambda(RDS と同じ VPC)。兄弟の ai-novel-core と同じ形にしてある。

| 何を | きっかけ | 仕組み |
| --- | --- | --- |
| 画面(`source/front`) | `main` への push | Amplify が GitHub を見て、[amplify.yml](../../amplify.yml) で建てる。ビルドの中で Cognito(`source/front/amplify`)も建てる |
| API(`source/back`) | `main` への push のうち `source/back` の変更 | `.github/workflows/deploy-api.yml`(image を建てて ECR へ、マイグレーション、Lambda の差し替え) |
| 土台(ECR・Lambda・CI のロール) | 手元から `cdk deploy` | `infra/`(CDK) |

## 作りの決まり

- Lambda は RDS と同じ VPC の中に置き、NAT Gateway は置かない(月約 $45 を避ける)。そのため Lambda からは外へ出られない
- db へは IAM データベース認証で繋ぐ。トークンは Lambda の中で署名するので外へ出なくてよい(`app/db/session.py`)。RDS 管理のパスワードは定期的に替わるので、環境変数には埋めない
- Cognito の公開鍵も取りに行けないので、ID トークンはフロントの route handler(`source/front/src/app/api/v1/[...path]/route.ts`)が確かめ、利用者の `sub` を `x-archieves-user-*` ヘッダーで API に渡す。API は `AUTH_MODE=proxy`(`app/core/security.py`)
- API の関数 URL は `AWS_IAM`。呼べるのは Amplify の SSR のコンピュートロール(`ArchievesApi` が作る)と CI のロール(煙の確かめ)だけで、署名の無い要求は関数が起きる前に弾かれる。その上で合言葉(`x-archieves-api-key`。`app/core/api_keys.py`)も要る。`API_KEYS` が空だと API は起動しない
- db のロールは二つ。`archieves_migrator` が表の持ち主(マイグレーションの Lambda `archieves-migrate` が使う)、`archieves_app` は行の読み書きだけ(API の Lambda が使う)

## 初回の用意(一度だけ)

順番に意味がある(画面のビルドで作られる Cognito は、API の側では要らない。Amplify の環境変数は API の関数 URL ができてから置く)。

1. API の合言葉を SSM の SecureString に作る。`infra/` のスタックは synth のときにこれを読むので、無いうちは `cdk` が止まる

   ```
   aws ssm put-parameter --name /archieves/api-keys/web --type SecureString --value "$(openssl rand -hex 32)"
   ```

2. `infra/aws.example.json` を `infra/aws.json` に写して埋める(git には入れない)。GitHub の OIDC の `sub` が immutable subject の形(`repo:<owner>@<ID>/<repo>@<ID>`)なら、`gh api repos/<owner>/<repo>/actions/oidc/customization/sub` の `sub_claim_prefix` を `github.subClaimPrefix` に置く
3. `infra` で `npm install` し、ECR と CI のロールを作る

   ```
   npx cdk deploy ArchievesCi
   ```

   出力の `DeployRoleArn` を、リポジトリの秘密 `AWS_DEPLOY_ROLE_ARN` に置く
4. db とロールを作る。マスターで RDS に繋ぎ(`ローカル開発からのRDSアクセス.md` の踏み台とトンネル)、`postgres` db に対して流す

   ```
   psql -v ON_ERROR_STOP=1 -f infra/sql/archieves_roles.sql
   ```

5. 最初の image を手元で建てて `main` の tag で push する(関数が無いと CI の `update-function-code` が落ちる)

   ```
   infra/lambda/push-image.sh
   ```

6. 関数を作る

   ```
   cd infra && npx cdk deploy ArchievesApi
   ```

   出力の `FunctionUrl`(API の関数 URL)と `AmplifyComputeRoleArn` は SSM の `/archieves/api/function-url`・`/archieves/amplify/compute-role-arn` にも出るので、あとから引ける
7. 最初のマイグレーションを流す(CI が回るまで待たずに当てるなら)

   ```
   aws lambda invoke --function-name archieves-migrate --cli-read-timeout 960 \
     --cli-binary-format raw-in-base64-out --payload '{}' /dev/stdout
   ```

8. GitHub のリポジトリの設定(Settings → Secrets and variables → Actions)

   | 種類 | 名前 | 値 |
   | --- | --- | --- |
   | Variables | `AWS_REGION` | `ap-northeast-1` |
   | Variables | `ECR_REPOSITORY` | `archieves-api` |
   | Variables | `LAMBDA_FUNCTION_NAME` | `archieves-api` |
   | Variables | `MIGRATION_FUNCTION_NAME` | `archieves-migrate` |
   | Secrets | `AWS_DEPLOY_ROLE_ARN` | 3 の `DeployRoleArn` |
   | Secrets | `API_BASE_URL` | 6 の `FunctionUrl`(任意。煙の確かめ用。末尾の `/` は除く) |

9. Amplify のアプリに、関数 URL を呼ぶコンピュートロールを付け、環境変数(アプリ全体)を置く。鍵の値は手で写さず、SSM から読んで置く

   ```
   aws amplify update-app --app-id <アプリの ID> \
     --compute-role-arn "$(aws ssm get-parameter --name /archieves/amplify/compute-role-arn --query Parameter.Value --output text)"
   ```

   | 名前 | 値 |
   | --- | --- |
   | `AMPLIFY_MONOREPO_APP_ROOT` | `source/front` |
   | `ARCHIEVES_API_URL` | 6 の `FunctionUrl` |
   | `ARCHIEVES_API_KEY` | 1 で作った鍵(`/archieves/api-keys/web` の値) |

   `NEXT_PUBLIC_AUTH_MODE` は置かない(既定の `cognito`)
10. `main` に push する。Amplify が画面を建て(Cognito もここで建つ)、`deploy-api` が API を差し替える

## ふだんの流れ

- `main` へのマージで、画面と API が自動で出る。API は db のマイグレーションを先に流し、そのあと Lambda を差し替える(失敗したら差し替えない)
- 列を消す・名前を変えるマイグレーションは、マイグレーションのあと Lambda を差し替えるまでの 1〜2 分、古い API が失敗しうる
- 画面と API の組み合わせがずれる(新しい画面が古い API を呼ぶ)ことがある。API を変える PR は、API の変更を先に `main` へ入れるか、互換を保つ形にする
- 土台(`infra/`)を変えたときだけ、手元から `cdk deploy`。CI からは `cdk deploy` を流さない(CI のロールを ECR への push と関数のコードの差し替えだけに絞るため)

## 利用者を作る

画面からの登録の可否は `source/front/amplify/auth` の設定に従う。Cognito のユーザープールの ID は、Amplify のビルドが書く `amplify_outputs.json` か、`aws cognito-idp list-user-pools` で分かる。
