# 料金プランと機能別認可

## 方針

- **基本料金は無料**。アカウントを作れば、自分の記録と自分の統計はすべて無料で使える。
- **有料はソーシャル領域**。ランキング／フィードと、コミュニケーション（組織内・グループ）機能を有料とする。
- ページ（ルート）単位・API単位で、**プランごとの認可**を通す必要がある。認証（誰か）だけでなく、
  認可（そのプランで使えるか）を機能ごとに判定する層を設ける。

無料と有料の線引きの理由は [ビジョン.md](ビジョン.md) の方向性に沿う。記録と統計は
「気軽に扱えるツール」としての根幹なので、ここを無料にして入口を広く保つ。
継続的なコストと価値が乗るのは他人との接点（ランキング、コミュニケーション）側なので、
そこを課金対象にする。

## プラン定義

| プラン | 課金単位 | 料金 | 主な範囲 |
| --- | --- | --- | --- |
| `free`（基本） | 個人 | 無料 | 自分の記録・自分の統計・自分のプロフィール |
| `social`（個人有料） | 個人 | 有料 | 全国ランキング／フィード、他ユーザーとの交流（コメント・リアクション） |
| `group`（グループ有料） | グループ | 有料 | 組織内コミュニケーション、メンバー管理、グループ全体統計 |
| `venue`（射場・団体） | 射場／連盟 | 有料 | 射場利用料・会費の一元管理（[アイデア.md](アイデア.md) の3番。本ドキュメントでは範囲外） |

`group` は所属メンバーへ権利が波及する。ユーザーの**実効プラン**は
「個人プラン ∪ 所属グループのプラン」で決まる（後述の entitlements）。

## 機能別の対応表

フロントの現行ルートを基準に整理する。

| ページ／ルート | 機能 | プラン |
| --- | --- | --- |
| `/` | ホーム | `free` |
| `/game/setup`, `/game/score-card` | 得点記録 | `free` |
| `/score-log` | 自分のスコア一覧 | `free` |
| `/score-view` | 自分の記録の閲覧 | `free` |
| `/analysis` | 自分の統計・命中座標の分析 | `free` |
| `/import` | 自分の記録の取り込み | `free` |
| `/profile/me`, `/profile/settings` | 自分のプロフィール | `free` |
| `/profile/matches` | 自分の試合結果の登録・閲覧 | `free` |
| `/profile/[sub]` | 他ユーザーのプロフィール閲覧 | `social` |
| `/ranking` | 全国ランキング・フィード | `social` |
| `/organization/[organizationId]` | 組織内コミュニケーション・メンバー管理・全体統計 | `group` |

対応するAPI側（archieves-api）も同じ区分で揃える。

| エンドポイント群 | プラン |
| --- | --- |
| `games`, `imports`, `users`（自分のリソース） | `free` |
| `statistics`（自分のスコアの集計） | `free` |
| `statistics`（全体との比較・ランキング系の集計） | `social` |
| `organizations` | `group` |

「自分の統計」と「全体との比較」は同じ統計エンドポイント群に同居しやすいので、
**パス／クエリの時点で分ける**（例: `/statistics/me` と `/statistics/ranking`）。
1つのレスポンスに無料分と有料分を混ぜると認可が書けなくなる。

## 認可の実装方針

3層に分けて考える。

### 1. 認証（既存）

Cognito。フロントは `AuthGate`（`src/components/auth/AuthGate.tsx`）、
バックは `get_current_user`（`app/core/security.py`）。ローカルは
`AUTH_MODE=mock` / `NEXT_PUBLIC_AUTH_MODE=mock` でAWSなしに動く。
プラン認可もこのmockモードで動かせること（モックユーザーのプランを
環境変数で切り替えられる）を前提にする。

### 2. プラン判定（entitlements）

課金状態の正はAPI側のDBに置く。Cognitoのカスタム属性やグループに持たせると、
解約・課金直後にトークンが古いままになり、再ログインするまで反映されない。
トークンからは `sub` だけを使い、プランはDBを引く。

- `GET /api/v1/users/me/entitlements` → `{ "plan": "social", "features": ["ranking", "feed"], ... }`
- フロントはこれを1度取得してキャッシュし、ページのガードとUI（アップセル表示）に使う。

### 3. 認可

- **バックエンド（唯一の強制点）**: エンドポイントにプラン要求の依存性を追加する。
  `app/api/deps.py` に `require_plan(Plan.SOCIAL)` のようなDependencyを置き、
  満たさなければ `403`（ボディで `detail: "plan_required"` と必要プランを返す）。
  `402 Payment Required` も候補だが、まずは扱いが安定している403で統一する。
- **フロントエンド（体験のため）**: ページ単位のガード。無料ページは素通りさせ、
  有料ページでは実効プランを見て、ブロックではなく**アップセル画面**を出す
  （何が見られるのかは示し、操作だけ止める）。これはセキュリティ境界ではないので、
  バック側の認可を省略しない。

実装のイメージ:

```
front: <PlanGate feature="ranking"> ... </PlanGate>   // 未加入ならアップセル
back : Depends(require_plan(Plan.SOCIAL))             // 未加入なら403
```

## データモデルの素案

- `subscriptions`: `user_id`, `plan`, `status`, `current_period_end`, 決済側のID
- `organization_subscriptions`: `organization_id`, `plan`, `seats`, `status`, `current_period_end`
- 実効プランは、上記2つと所属（`organization_members`）から都度算出する。
  ユーザー行に `plan` をコピーで持たない（解約・期限切れの反映漏れを避ける）。

## 原則

- 記録と自分の統計は**ずっと無料**にする。ここを後から有料に倒すと、
  自分のデータを人質に取る形になり、ツールとしての信頼を失う。
- 有料化はソーシャル／組織機能のみ。無料ユーザーが使えなくなる既存機能を作らない。
- 無料・有料の判定は必ずサーバー側で行う。フロントのガードは表示の都合。

## 未確定事項

1. **AIアドバイス**のプラン。[アイデア.md](アイデア.md) では個人課金側に置いていた。
   自分の記録に対する助言なので無料寄りにも見えるが、実コストが高い。保留。
2. **ランキングへの掲載**。閲覧を `social` にするとして、無料ユーザーが
   ランキングに載る側になるか（載るなら母数が増えて有料側の価値も上がる）。
3. **試合結果の公開**（[スコアログ.md](../機能アイデア/スコアログ.md)）は
   ソーシャル機能のベースだが、公開自体は無料にするか。
4. 無料プランに保存期間や記録数の上限を設けるか（現時点では設けない想定）。
5. エラーコードを `403` にするか `402` にするか。
