# AWSでなるべく安いPostgreSQL環境

前提: 個人開発〜小規模だが将来本番運用もありうる想定。東京リージョン(ap-northeast-1)、2026年8月時点のおおよその料金(変動あるので目安)。

## 選択肢比較

| 方式 | 月額目安 | メリット | デメリット |
| --- | --- | --- | --- |
| **EC2自前インストール** (t4g.micro + EBS gp3 20GB) | 約 $7〜8 | 圧倒的に安い。構成の自由度が高い | OS/PostgreSQLのパッチ・バックアップ・監視を自分で運用する必要がある |
| **Lightsail マネージドDB** (Standard, 1GB RAM/40GB SSD) | $15固定 | 料金が固定でわかりやすい。バックアップ・パッチ適用が自動 | スペック変更の柔軟性が低い。EC2よりは割高 |
| **RDS for PostgreSQL** (db.t4g.micro + gp3 20GB) | 約 $25〜30 | フルマネージド。自動バックアップ、Multi-AZ、リストアが容易 | 選択肢の中では最も高い |
| **Aurora Serverless v2** | 約 $40〜(最小0.5ACU) | 自動スケール、使わない時間帯は縮小 | 最小構成でも常時課金が発生し、小規模用途では逆に割高になりやすい |

- EC2は無料利用枠(750時間/月)が2025年7月以降の新規アカウントでは廃止済み。t4g.smallのみ2026年末まで無料トライアルが継続中。
- ストレージはどの方式でもEBS gp3ベースなら1GBあたり月$0.096〜0.115程度が目安。

## 結論: 最安を狙うならEC2自前構築

「なるべく安く」を最優先にするなら **EC2 (t4g.micro or t4g.small) にPostgreSQLを直接インストール** が最も安い。
ただし本番運用も見据えるなら、以下の運用コストを許容できるかを事前に検討する。

- OSパッチ・PostgreSQLのマイナーバージョンアップは自分で実施
- バックアップはEBSスナップショットの定期取得を自分で設定(cron + AWS CLI、またはAWS Backup)
- 単一AZ構成になるため、AZ障害時は落ちる(Multi-AZが必要ならRDSへの移行を検討)
- 見えないコスト(自分の作業時間)を考慮する

小規模でも「運用の手間をかけたくない」場合はLightsailマネージドDBが固定$15/月で妥協点として良い。

## 構築手順(EC2自前インストール)

### 1. インスタンス起動

- インスタンスタイプ: `t4g.micro` (2vCPU/1GB, Graviton, ARM64) ※メモリが厳しければ `t4g.small` (2GB)
- AMI: Amazon Linux 2023 (ARM64)
- ストレージ: gp3, 20GB程度から(必要に応じて拡張)
- セキュリティグループ: 5432番ポートは自分の開発環境のIP、またはアプリケーションサーバーのセキュリティグループのみに限定(0.0.0.0/0は厳禁)

### 2. PostgreSQLインストール

```bash
sudo dnf update -y
sudo dnf install -y postgresql16 postgresql16-server
sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql
```

### 3. 初期設定

- `postgresql.conf` の `listen_addresses` をアプリケーションサーバーからの接続に合わせて設定(全開放しない)
- `pg_hba.conf` で接続元IP/セキュリティグループを絞る
- 管理用ユーザーのパスワードを設定し、アプリ用ユーザー/DBを個別に作成(rootユーザーを直接使わない)

### 4. コスト最適化のポイント

- Elastic IPは使う場合のみ確保(未アタッチ状態は課金対象)
- 開発用途で常時起動不要なら、夜間/週末はインスタンス停止でEC2稼働時間そのものを削減できる(EBS分の料金は停止中も発生)
- リザーブドインスタンス/Savings Plansは1年以上の運用が確定してから検討(小規模開発初期はオンデマンドで様子見でよい)

### 5. バックアップ運用

- 最低限、EBSスナップショットを日次で自動取得(AWS Backupのバックアッププランが簡単)
- `pg_dump` によるロジカルバックアップも併用し、S3に定期エクスポートしておくとより安全

## 将来的な移行の目安

- サービスが成長してダウンタイムが許容できなくなったら、RDS(Multi-AZ)への移行を検討
- 移行は `pg_dump`/`pg_restore` またはAWS DMSでほぼ無停止移行が可能
